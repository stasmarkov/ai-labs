# Ship report: spec-20261113-2230-mcp-listing-tools (SL-35 MCP server for the listing tools)

## Summary

SL-35 adds a local, opt-in MCP server (`ddev exec php artisan mcp:start listings`) that exposes the SL-34 listing tools to outside clients. It has four read tools (`search_listings`, `get_listing`, `count_by_tag`, `change_status`) and two propose tools (`propose_title_change`, `propose_tag`). A proposal only stores a pending change and returns a URL. A human applies it by confirming at `/ai/changes/{id}`, and every tool call is logged to `mcp_tool_calls`. The live journey works end to end and all gates are green. The build is not finished, though: tasks 1, 2, 3 and 6 are reported incomplete, two converge gaps (14 and 15) are unbuilt, and review confirmed a major security hole that lets the MCP client confirm its own change. **Recommendation: FIX-FIRST.**

## Confirmed review findings

### Major

- **`routes/web.php:54`** (security): the MCP client can confirm its own change. It can GET the page for the cookies, then POST with `X-XSRF-TOKEN` and no `Sec-Fetch-Site` header, which passes the CSRF check and `RefuseCrossSiteRequests`. This breaks NFR-1, and it makes the "you cannot confirm it" note false. Fix: require proof the client cannot get, such as a per-change nonce that only the rendered page carries and that is checked against the session. Or reject requests whose `Sec-Fetch-Site` is missing or not `same-origin`, add an Origin check, and record the remaining headless-browser risk in the guide.
- **`app/Services/PendingChangeDecisionService.php:31`** (design): claim, apply and settle are three separate commits. A crash after the claim leaves the row `applying` forever: `change_status` reports it as `pending`, and the row drops out of both lists. Fix: run the conditional claim (or `SELECT ... FOR UPDATE`), apply and settle in one transaction, and drop the internal `applying` state.
- **`app/Services/PendingChangePageService.php:55`** (performance): N+1. `present()` runs `findByPendingChange` for each of up to 70 list rows. Fix: skip the lookup for list rows, or batch-load it with one `whereIn('pending_change_id', $ids)`.
- **`app/Services/PendingChangePageService.php:34`** (performance): each list row carries the full arguments, preview, result and proposed_by, which the list never renders. Fix: send a slim list DTO (`id`, `tool`, `status`, `expires_at`) and keep the full presentation for the single `change` prop.

### Minor

- **`app/Services/PendingChangeDecisionService.php:31`** (correctness): any exception between claim and settle (from `validate()`, `find()` or `settle()`) leaves the row stuck in `applying`. Fix: wrap apply and settle in `try/catch (Throwable)` and settle the row as `failed`. Also treat an overdue `applying` row as failed or expired in `effectiveStatus`.
- **`app/Services/ChangeProposalService.php:40`** (correctness): the `propose_tag` preview has no 20-tag cap. An oversized reply becomes `result_too_large`, so the client loses the change id and URL while the change stays stored. Fix: cap the preview tags with `AdminArguments::tagsShown()`, and cap the preview before building the reply so `change_id` and `url` always survive.
- **`resources/js/ai/Pages/Lab/Changes.vue:66`** (correctness): `decide()` replaces only `shown`. The pending and decided lists never refresh, and after a 409 the card still shows the buttons. Fix: call `router.reload({ only: ['pending', 'recent'] })`, and refresh the shown change on a 409.
- **`resources/js/ai/Pages/Lab/Changes.vue:100`** (correctness): pending list items show no preview and no Confirm or Reject buttons, the list shows the internal tool name, and the C-13 "make model" fallback for a null `old_title` is never applied. Fix: pass the preview and the confirm and reject URLs in the list props, and render them per item (gap 14).
- **`app/Services/PendingChangeDecisionService.php:40`** (security): an exception class name (for example `Illuminate\Database\QueryException`) reaches the MCP client through `change_status`. Fix: store a stable code such as `apply_failed` and keep the class name in logs.
- **`app/Services/ChangeProposalService.php:39`** (security): the preview is a snapshot from proposal time, but confirm overwrites the listing's current state. Fix: rebuild the preview on page load, or store the expected `old_title` and fail the confirm when it no longer matches.
- **`app/Services/ChangeProposalService.php:43`** (design): the URL is built from the hard-coded path `url('/ai/changes/'.$id)`. Fix: use `route('ai.changes.show', ['id' => $stored->id])`.
- **`app/Providers/AppServiceProvider.php:141`** (design): the MCP start gate splits the exports rate-limit comment from its limiter, it sits outside `AiServiceProvider`, and it matches the raw token `listings` anywhere in argv. Fix: move it to `AiServiceProvider` and match the command's `handle` argument.
- **`resources/js/ai/Pages/Lab/Changes.vue:49`** (design): `csrfToken()` is now copied a third time, after `PhotoDuplicates.vue` and `Photos.vue`. Fix: extract a shared `useLabFetch` composable in `resources/js/ai/composables`.
